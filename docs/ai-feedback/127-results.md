# #127 절약 시뮬레이션 — 방법·실현 가능성 코드 계산, 그날 기준 재계산

PR #128에서 이중 차감·월말 예측 기준·연 환산 오류는 이미 고쳤다. 이번 작업은 남은 두 가지다.

1. 방법·실현 가능성을 LLM이 아니라 거래 데이터에서 코드로 계산한다.
2. 시뮬레이션을 열 때 피드백 분석을 오늘 날짜로 다시 계산하고, 피드백과 비교해 보여준다.

## 변경

- `SavingsMethodAnalyzer`(신규, 순수 계산)
  - 방법: 이번 달 횟수·건당 평균으로 남은 기간 예상 횟수를 구하고 감축액을 "N번 덜 쓰기(예상 A번 → B번)" 또는 "한 번에 X원꼴 → Y원꼴"로 바꾼다. 이번 달 거래가 없으면 직전 3개월 기록으로 추정한다.
  - 실현 가능성: 필요 감축 비율(감축액 ÷ 남은 기간 예상 지출), 과거 달성 이력(지난 3개월 중 목표 수준 이하로 쓴 달), 감정 구성(만족 50%↑ 어려움, 충동·후회 50%↑ 쉬움), 거절 이력을 점수로 더해 EASY/NORMAL/HARD와 근거 문장을 낸다.
- `AiFeedbackService.computeActionsAsOf(userId, asOf)`: `generateWeekly`와 같은 계산(월말 예측 → 초과 → 원인 → 절약 액션)을 LLM·저장·이벤트 없이 기준일 하루에 대해 다시 한다. payload에 `savingsGapWon`(저축 목표까지 부족액)을 저장한다.
- `SavingsSimulationService`: 진행 중인 달이면 오늘 기준 재계산 결과를 쓴다.
  - 카드마다 `source`: `FEEDBACK`(피드백에서 제안한 카테고리) / `NEW`(피드백 이후 새로 초과 예상). 더 줄일 필요가 없어진 카테고리는 보이지 않는다.
  - 문구(현재 행동·목표 행동·패턴)는 피드백에 저장된 것을 같은 카테고리에 이어 쓰고, NEW는 문구 없이 코드 방법·실현 가능성만 보여준다. 요청마다 LLM을 부르지 않는다.
  - 응답 `comparison`: "11/9 피드백 이후 저축 목표까지 부족액 29만 원 → 33만 원".
  - 지난 달이거나 재계산에 실패하면 피드백에 저장된 액션을 그대로 쓴다.
- 카드에 `method`, `feasibilityLevel`, `feasibilityReasons`, `source`, `feedbackReductionWon` 추가. 기존 `feasibilityScore`는 유지.

## 측정 (테스트 데이터, LLM 없음, `SIM_MEASURE=1 ./gradlew test --tests "*simulationMeasure" -i`)

ALERT이고 절약 액션이 있는 29주.

| 지표 | 결과 |
|---|---|
| 일요일 기준 재계산 = 그 주 피드백에 저장된 액션 | **29/29주** — 재계산이 피드백과 같은 계산임을 확인 |
| 같은 주를 월요일에 열었다면(주 단위 저장 가정) 액션이 일요일과 다름 | **29/29주** |
| 그중 카테고리 구성이 다름 | 21/29주 |
| 겹치는 카테고리의 감축액 평균 차이 | 61,118원 |
| 방법을 만들 수 있었던 카드 | 59/60 |
| 실현 가능성 분포 | 쉬움 10, 보통 28, 어려움 22 |
| 빈도 방식 방법의 (덜 쓸 횟수 × 건당 평균)이 감축액과 ±50% 이내 | 42/45 |

주 단위로 저장해 두고 보여줬다면 모든 주에서 주 후반(일요일 이후)에는 감축액이 달랐고 세 주 중 두 주 넘게 제안 카테고리 구성까지 달랐다. 그래서 열 때마다 그날 기준으로 계산한다.

## 한계

- **LLM 문구의 정확도는 측정하지 못했다.** 현재 행동·목표 행동 문구가 데이터와 맞는 비율은 API 호출이 필요해 이번에 재지 않았다. #131에서 넣은 형식 검사(숫자 개수·수치 목표 표현 제외)가 그대로 적용된다. 방법·실현 가능성은 문구가 아니라 코드 계산이라 이 문제를 비켜 간다.
- 실현 가능성 점수의 가중치(감축 비율 구간 20%/40%, 달성 월 수, 감정 50% 기준)는 설계 값이며 사용자 반응으로 검증하지 않았다. 등급 분포가 보통·어려움에 치우친 것은 감축 비율이 큰 주가 많기 때문이고, 구간 값은 데이터가 쌓이면 조정한다.
- 방법 문구의 횟수는 일 평균 기반 예상이라 실제 소비 패턴(요일 편중)은 반영하지 않는다.
- "예산에 반영(apply)" 동작은 이슈 범위 밖이라 바꾸지 않았다. 다만 apply도 오늘 기준 재계산 금액을 쓴다.
- 재계산은 요청마다 지출 윈도우를 조회하므로 응답 시간이 늘 수 있다. 사용자당 한 번 조회 수준이라 측정하지는 않았다.
