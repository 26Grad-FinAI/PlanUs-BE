# #144 주간 피드백 첫 문장·비율·속도 표기 개선 결과

측정일 2026-11-18. 판정 기준은 [judging-rubric.md](judging-rubric.md), 판정 방법은 [140-results.md](140-results.md)와 같다.

## 왜 했나

#140 블라인드 측정에서 현재 코드(v4.1)는 이번 주 총지출을 말하지 않는 응답이 87%였고, 사실 오류의 대부분이 "이번 주 … 이번 달 예산의 N%"(누적 비율을 이번 주에 붙임), 이번 주는 줄었는데 "이번 주는 빠른 편"(이번 달 속도를 이번 주에 붙임), 전주 비교를 "평소"로 쓰는 문장이었다. 판정 중 판정자가 "이번 주에 얼마 썼는지, 평소(지난 4주 평균) 대비 얼마인지 알려 달라", "215,001원을 줄이라는 게 얼마에서 줄이라는 건지 모르겠다"고 지적했다.

## 해석

1. **목표한 오류는 줄었다.** 첫 문장에 이번 주 총지출이 빠진 응답 0건(재시도·코드 대체 없이 LLM이 처음부터 씀), 대상기준 오류 26 → 1건, 내부용어 6 → 0건.
2. **새 정보를 넣자 조언 품질 오류가 생겼다.** v4.2에서 "숫자는 총지출 외 2개" 규칙 때문에 절약 액션 3개 중 2개만 말하면서 3개를 다 지켰을 때의 효과를 붙이고, 좋은 예의 "이번 달 전체로는 빠르게"를 느린 주에도 옮겨 썼다. v4.3 검사로 일부 줄었지만(18.2% → 13.6%, 유의하지 않음) 형태를 바꿔 남았다 — 한 카테고리만 지켰을 때의 효과를 두 카테고리에 붙이거나, "가장 컸다"를 실제로 가장 크지 않은 거래에 쓴다.
3. **검사 추가의 비용.** 렌더당 호출 1.10 → 1.38회(+25%), 1차 통과 91% → 70%. LLM이 금액을 비교·계산하는 문장(절약 효과, '가장 큰 것')은 검사를 늘려도 형태를 바꿔 남으므로, 그 문장을 코드로 만들거나 구조화 출력으로 주장마다 근거를 대조하는 방식이 다음 단계다 (#146).

## 한계

- #140과 같은 23주로 고치고 쟀다 — v4.2를 본 뒤 v4.3을 만들었으므로 v4.3 수치는 특히 낙관적일 수 있다. 새 데이터로 확인해야 한다 (#143).
- 판정은 LLM 판정기(#140에서 검증, 사실 오류 독립 κ 0.20 / 합의 후 0.93, 총지출 누락 독립 κ 0.93).
- 사용자 1명, 8~11월 균등 예산 (#142).

## 재현

```
# 각 버전 커밋에서 응답 생성 (ANTHROPIC_API_KEY 필요)
LLM_REPEAT=3 ./gradlew testLlm --tests "*ProductionPathValidationTest.productionPath_render"

# 블라인드 시트 → LLM 판정기 → 지표별 집계
./gradlew judge -Pcmd=export -Pout=<폴더> -Pkinds=주간 -Plogs="v4.1=a.log;v4.2=b.log"
./gradlew judge -Pcmd=llm -Pdir=<폴더> -Pout=<결과>.csv
./gradlew judge -Pcmd=score -Pkey=<폴더>/_key/key.csv -Psheets="<결과>_사실오류.csv"
```

판정기 비용: v4.1·v4.2 135건 약 $4, v4.3 66건 약 $2. 측정 로그·판정 시트는 거래 메모가 들어 있어 저장소에 올리지 않았다.
