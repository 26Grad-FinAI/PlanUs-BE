# #124 LLM 클라이언트 장애 대응 결과

가짜 LLM 서버(`LlmFailureScenarioTest`)로 장애를 재현해 개선 전·후를 같은 입력(사용자 20명 순차 처리)으로 비교했다. API 키는 쓰지 않았다.
"개선 전"은 같은 코드에서 재시도 0회·서킷 없음·전체 상한 없음으로 설정한 것으로, 이전 동작과 같다.

## 측정 결과

| 시나리오 | 지표 | 개선 전 | 개선 후 |
|---|---|---|---|
| 크레딧 소진(400, 계속) | 상류 호출 수 | 20 | **1** |
| 크레딧 소진(400, 계속) | 배치 시간 | 110ms | 11ms |
| 일시 과부하(529, 앞 2회만) | 템플릿 폴백한 사용자 | 2명 | **0명** |
| 서버 장애(500, 계속) | 상류 호출 수 | 20 | 15 (연속 실패 5회 뒤 서킷 열림) |
| 헤더 뒤 본문 정지 | 호출 1건 시간 | 읽기 타임아웃에 의존 | 전체 상한(1초 설정)에서 1016ms에 끊김 |

가짜 서버가 즉시 응답하므로 시간은 절대값이 아니라 호출 수와 폴백 수가 의미 있다. 실제 API가 느리면 영구·장기 장애 때 배치 시간 차이가 훨씬 커진다(건너뛴 호출 수 × 호출당 지연).

## 변경

- `LlmCallGuard`(신규): 오류 분류, 재시도, 전체 시간 상한, 서킷 브레이커, 통계.
  - 429·529·5xx·연결/읽기 실패는 일시 장애로 보고 백오프(1초, 2초)로 최대 2회 재시도.
  - 그 밖의 4xx(400 크레딧·401 키)는 영구 장애로 재시도 없이 서킷을 바로 연다.
  - 호출 하나(재시도·대기 포함)의 전체 상한 60초. 넘으면 스레드를 중단시킨다.
  - 일시 장애가 연속 5회면 서킷을 열고 5분간 호출 없이 템플릿으로 보낸다. 쿨다운 뒤 호출 하나만 통과시켜 성공하면 닫는다.
- `AnthropicLlmClient`: 위 보호를 적용. 기준 URL·타임아웃·재시도·서킷 값을 `planus.ai.llm.*`로 설정 가능하게 했다.
- 주간·월말 배치: 끝날 때 `LLM 호출 성공=… 일시장애=… 영구장애=… 시간초과=… 서킷건너뜀=… 평균지연=…ms`를 로그로 남긴다.
- `ActionEnricher`(Spring AI): 기본 재시도는 10회·최대 3분 대기였다. `spring.ai.retry.max-attempts=3`, 백오프 1s→10s, `spring.http.client` 연결 5초·읽기 60초로 줄였다. 크레딧·키 오류(4xx)는 재시도하지 않고 기본 actions로 폴백하는 기존 경로를 쓴다.

## 한계

- 26분 멈춤은 재현하지 못했다. 헤더 뒤 본문이 멈추는 경우도 읽기 타임아웃(2초 설정)에서 2.3초에 끊겼다. 원인은 여전히 미확인이고, 전체 시간 상한이 어떤 원인이든 호출당 60초에서 막는 안전망이다.
- Spring AI 경로의 재시도·타임아웃은 설정만 바꿨고 실제 호출로는 측정하지 않았다(API 키 필요). 서킷 브레이커도 이 경로에는 적용되지 않는다.
- 서킷 상태는 서버 인스턴스별 메모리에 있다. 배치는 ShedLock으로 한 인스턴스만 돌므로 문제 없지만, 여러 인스턴스가 사용자 요청으로 LLM을 호출한다면 인스턴스마다 따로 열린다.
